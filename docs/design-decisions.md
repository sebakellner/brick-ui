# Design decisions

Rationale behind the current shape of the kit. The README covers usage; this
file covers why the pieces are arranged this way, and what is still missing.

## Tokens are generated

`tokens/*.json` is the source of truth; `src/styles/tokens/*.css` is generated by
Style Dictionary 5 and committed, so a checkout works without a build step.

Aliases are authored as references and emitted as `var()` thanks to
`outputReferences`, which keeps two properties that a values-only pipeline would
destroy: cross-layer aliasing resolves at runtime, and a host can re-theme a
subtree by setting custom properties on any ancestor.

CI reruns the build and fails when the generated CSS does not match the source,
including untracked output that nobody staged.

## Three layers of color

```
--bk-palette-*          raw palette, referenced only by the layers below
  └── --bk-color-*      shared roles: muted text, muted surface, strong border,
      │                 danger, focus ring
      └── --bk-button-{variant}-* / --bk-input-*   what a control paints
```

No component holds a literal color, so re-theming a variant is a token edit.

Ten semantic roles were removed after the controls took their own layer: they
had no consumer left. Two palette entries lost their last consumer with them
(`orange-900`, `stone-700`) and stay, because a palette is a reference ramp, not
a usage list.

## Two rules that keep the scales honest

- **Space is the only rhythm.** `--bk-space-base` is 4px and every step derives
  from it. Don't add a step off the grid.
- **Radius has no scale of its own.** It aliases space: `-sm` = space 1, `-md` =
  space 2, `-lg` = space 4. A corner that needs 14px is a design decision, not a
  token.

## Three kinds of custom property

- **Declared tokens** are the defaults in the generated CSS.
- **Component internals** are `--bk-button-variant-*`: a component sets them on
  `:host` from its control tokens so a public hook can win first. Not part of
  the contract; don't override them.
- **Override hooks** are read by a component and declared nowhere, so they always
  win over a variant default even when inherited from an ancestor:
  `--bk-button-bg`, `-bg-hover`, `-fg`, `-border`, `-border-hover`,
  `--bk-button-radius`, `--bk-input-radius`.

## The theme is required

Components used to carry a hard-coded fallback per token
(`var(--bk-button-bg, #c2410c)`), which promised that a page could skip
`theme.css`. Nothing ever exercised that path — the playground and Storybook both
load the theme — while the fallbacks duplicated ~50 values from the token source.
That is the drift you cannot see: change a palette entry, rebuild, and the
fallback keeps painting the old brand color with no error.

The fallbacks were removed. Defaults now live once, in the generated CSS, which
is what Shoelace and Spectrum Web Components do: a component without its theme
is visibly unstyled, and a visibly unstyled component gets fixed. Composite
fallbacks survived where they express composition rather than a value, e.g.
`var(--bk-button-bg, var(--bk-button-variant-bg))`.

Tests load the real stylesheet through `src/test/helpers/theme.ts`, so the suite
exercises the configuration people actually use. The helper memoizes its promise:
each test file calls it from `before`, and a fresh link per call would stack
duplicate stylesheets in the same page.

The focus ring is a token too (`--bk-focus-ring-width`, `--bk-focus-ring-offset`,
both in `base.css`), so the components keep no style literals at all. Unifying
the offset settled both controls on 1px, the value the input already used.

## What the tests cover

Behaviour (accessibility wiring, events, disabled propagation) plus computed
styles: each control token, the variant mapping, override precedence, and the
invalid border that has to survive a hover. Hover is dispatched through
`@web/test-runner-commands`, because a class-swap simulation cannot lose a
specificity battle and would stay green through that bug.

Mutations that must fail the suite: inverting the hook/variant precedence, going
back to `font-family: inherit` on the button, letting `input:hover` win over
`input[aria-invalid='true']`, and dropping the theme from the test setup.

## Known gaps

- `bk-input` marks its message region with `data-state="helper"`, but only
  `error` has a style rule; helper text inherits the neutral message color.
- No visual regression coverage: computed styles are asserted, geometry is not.
- Chrome is the only browser in the suite.
- Not publishable yet: no `exports`, no `types`, no `LICENSE`, no `files`
  allowlist, and no build step that emits JS plus `.d.ts`.
- The two components still type their tokens as strings inside `css\`\``
  templates, so a typo in a token name is caught by review, not by `tsc`.
